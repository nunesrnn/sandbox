PADRÃO PREVI - NOTEBOOK SILVER DE SEGMENTAÇÃO CRM / DATA CLOUD OBJETIVO Este tipo de notebook é utilizado em stories de CRM, Salesforce e Data Cloud que envolvem automatização de segmentações e jornadas. Diferente de um notebook Silver tradicional, o objetivo não é apenas tratar dados. O objetivo principal é: Regra atual da jornada ↓ Entender como funciona ↓ Descobrir quais dados ela utiliza ↓ Identificar as fontes ↓ Validar a lógica ↓ Construir uma Silver para consumo do Data Cloud O foco é reproduzir a regra existente antes de pensar em melhorias. A prioridade é manter aderência ao comportamento atual da jornada. ------------------------------------------------------------------------------- PRIMEIRO PASSO DA STORY O primeiro passo não é criar uma Silver. O primeiro passo é analisar a query original enviada pelo solicitante ou especialista de negócio. Normalmente essa query vem: - Data Factory - Oracle - Processo legado - Automação antiga A query original é considerada a referência funcional da regra. Ela serve para responder: "O que a segmentação precisa entregar?" ------------------------------------------------------------------------------- ANÁLISE DAS TABELAS DA QUERY Antes de construir qualquer tabela nova, deve-se investigar as tabelas utilizadas pela query original. Objetivo: Descobrir se já existe alguma tabela que, sozinha, resolve a necessidade da story. Estratégias possíveis: 1. Executar consultas exploratórias nas tabelas citadas. Exemplos: - visualizar colunas - visualizar amostras - contar registros - verificar qualidade - validar presença das informações desejadas 2. Utilizar o Genie Agent (Dadinho). O Dadinho é uma IA da Previ que consegue realizar buscas amplas e contextualizadas dentro do ambiente Databricks. Nesse cenário deve-se gerar um prompt detalhado contendo: - contexto da story - objetivo da jornada - atributos necessários - query original - tabelas investigadas - dúvidas atuais ------------------------------------------------------------------------------- RESULTADO MAIS COMUM DA INVESTIGAÇÃO Na maior parte dos casos: Nenhuma tabela individual resolve a story inteira. Normalmente acontece o seguinte: Tabela A possui CPF e Nome Tabela B possui Email Tabela C possui Telefone Tabela D possui indicadores de negócio Por isso a query original costuma possuir JOINs. Esses JOINs normalmente são responsáveis por montar a audiência final. Quando isso acontece: A audiência construída pela query passa a ser o principal candidato para originar a nova Silver. ------------------------------------------------------------------------------- ADAPTAÇÃO DA QUERY A query recebida raramente é utilizada exatamente como foi entregue. Geralmente são realizados ajustes como: - adaptação para Spark SQL - correções de sintaxe - substituição de funções incompatíveis - melhorias de legibilidade - ajustes de aliases - remoção de filtros explicitamente descartados pelo negócio Importante: Não alterar regras de negócio sem validação funcional. Objetivo: Mesma regra ↓ Nova implementação e não: Nova regra ↓ Nova implementação ------------------------------------------------------------------------------- ESTRUTURA TÍPICA DO NOTEBOOK CÉLULAS FIXAS 1. Markdown Inicial Contém: - Story - Objetivo - Contexto - Origens - Referências encontradas - Silver prevista - Squad - Estratégia - Restrições de segurança ------------------------------------------------------------------------------- 2. Construção da Audiência Normalmente: CREATE OR REPLACE TEMP VIEW ou DataFrame final da audiência. Essa view representa o resultado da regra da segmentação. Exemplo: vw_publico_posse ------------------------------------------------------------------------------- 3. Amostra da Audiência Objetivo: Validar visualmente os dados produzidos. Exemplo: SELECT * FROM vw_publico_posse LIMIT 100 ------------------------------------------------------------------------------- 4. Escrita da Silver Objetivo: Persistir a audiência como tabela Silver. Origem da Silver: A view construída anteriormente. Exemplo: df_silver = spark.sql("SELECT * FROM vw_publico_posse") Escrita inicial sempre em DEV. ------------------------------------------------------------------------------- CÉLULAS CONTEXTUAIS São adicionadas apenas quando a story exige validações específicas. ------------------------------------------------------------------------------- Validação de Qualidade da Audiência Valida: - total de registros - CPFs distintos - CPFs duplicados - CPF nulo - Email nulo - Celular nulo - Sem canal de contato - Quantidade PFUT - Quantidade CAPEC - Faixa de idade - Tempo de posse ------------------------------------------------------------------------------- Validação de Duplicidades Objetivo: Verificar se CPFs repetidos são: - erro técnico ou - registros legítimos da origem Normalmente compara: QTD_REGISTROS versus QTD_VARIACOES ------------------------------------------------------------------------------- Validação de Extremos Objetivo: Investigar comportamentos anormais. Exemplos: - idades muito altas - datas antigas - datas futuras - distribuições inesperadas ------------------------------------------------------------------------------- Validação de Cobertura Objetivo: Confirmar se os atributos importantes realmente existem. Exemplos: - CPF - Nome - Email - Celular - PFUT - CAPEC ------------------------------------------------------------------------------- ESCRITA DA SILVER Por enquanto a primeira gravação ocorre em DEV. Padrão: catalogo_previ_dev A gravação em PROD só ocorre após homologação. Nunca escrever diretamente em PROD durante a investigação. ------------------------------------------------------------------------------- FILOSOFIA DESSE TIPO DE STORY Receber a query original ↓ Entender a regra de negócio ↓ Investigar tabelas utilizadas ↓ Verificar se alguma tabela já resolve a demanda ↓ Caso não resolva, utilizar os JOINs da regra original ↓ Construir audiência consolidada ↓ Executar validações ↓ Criar Silver em DEV ↓ Homologar para consumo do Data Cloud O objetivo não é descobrir uma regra melhor. O objetivo é reproduzir corretamente a regra atual da jornada dentro de uma arquitetura governada e automatizada.
